# 🏭 ربات‌ساز (Bot Factory) — نسخه ۳

سیستم فروش ربات Bulk Sender — مشتری حساب را از طریق **پیوی پشتیبانی** شارژ می‌کند،
سفارش (پلن + توکن) را داخل ربات ثبت می‌کند و **پشتیبانی ایمیج ربات را می‌سازد**
(حالت ساخت دستی — `MANUAL_BUILD_MODE=true`). در صورت تمایل، با یک دکمه همان رفتار
خودکارِ قدیمی (دیپلوی فکتوری در ~۱۰ ثانیه) هم قابل اجراست.

```
مشتری 🧑‍💼 ── سفارش+رسید ──▶ ربات فروش 🤖 ── تأیید ادمین ✅ ──▶ صف دیپلوی 🔧
                                                                    │
   پروکسی سالم 🟢 ◀── استخر مرکزی + تست مداوم ◀──────────────────────┤
                                                                    ▼
        MySQL مشترک (sender_1, sender_2, …) + Redis اختصاصی + ایمیج مشترک sender_bot:v1
                                                                    │
   مشتری 🧑‍💼 ◀── «ربات شما آماده شد: t.me/YourBot» ◀── health-check ✅
```

## 📦 محتویات بسته

| مسیر | توضیح |

| `core/orchestrator.py` | موتور ساخت/توقف/حذف اینستنس‌ها + تخصیص خودکار پروکسی |
| `core/deploy_queue.py` | صف دیپلوی چندکارگره (کارگر/ظرفیت صف از .env — هضم موج سفارش‌های همزمان) |
| `core/proxy_manager.py` | استخر مرکزی پروکسی: تست مداوم + سینک اختصاصی به هر اینستنس |
| `core/instance_proxies.py` | 🎯 موتور مدیریت تفکیک‌شده پروکسی هر اینستنس (تخصیص/ویرایش/تست/توزیع بار) |

| `scripts/` | build ایمیج + بکاپ شبانه |

## ⚡ نصب سریع (روی VPS)

**پیش‌نیاز:** Ubuntu 22.04+ با **۸ vCPU / ۳۲GB RAM** برای ۵۰ مشتری همزمان (۵۰×512m = 25.6GB سقف + MySQL/Redis/سیستم) — و دسترسی root.
سرور 16GB هم تا ~۲۵ اینستنس جواب می‌دهد اگر `INSTANCE_MEM_LIMIT=256m` و `INSTANCE_CPUS=0.25` بگذارید.

```bash
# ۱) آپلود بسته و سورس پروژه
scp bot_factory.zip root@SERVER:/opt/
scp sender_bot_project.zip root@SERVER:/opt/       # سورس Bulk Sender خودتان

ssh root@SERVER
cd /opt && unzip bot_factory.zip && unzip sender_bot_project.zip -d /opt/factory/source/
mv /opt/factory/source/sender_bot_project /opt/factory/source/sender_bot
mv /opt/bot_factory /opt/bot_factory               # یا هر مسیر دلخواه

# ۲) پر کردن تنظیمات
cd /opt/bot_factory
cp .env.example .env && nano .env                  # توکن ربات فروش + ADMIN_IDS + رمزها
chmod 600 .env

# ۳) نصب خودکار (Docker + MySQL + Redis + سرویس)
bash setup.sh

# ۴) ساخت ایمیج مشترک (یک بار برای همیشه)
bash scripts/build_sender_image.sh

# ۵) تست مانیتوری — لاگ ربات فروش:
journalctl -u bot-factory -f
```

> 🐳 **حالت کانتینری اختیاری:** اگر ترجیح می‌دهید ربات فروش هم Docker اجرا شود،
> `Dockerfile` موجود است (شامل docker CLI برای کنترل کانتینرها از طریق docker.sock) —
> بلاک کامنت‌شده‌ی `factory_bot` در انتهای `docker-compose.yml` را از کامنت خارج
> کنید، در `.env` مقدار `DB_HOST=factory_mysql` بگذارید و به‌جای systemd همان
> compose را بالا بیاورید. حالت پیش‌فرض (systemd روی هاست) ساده‌تر و قابل دیباگ‌تر است.

در تلگرام: به ربات فروش `/start` بدهید → یک سفارش تستی کامل ثبت کنید →
در اکانت ادمین دکمه «✅ تأیید و دیپلوی» را بزنید → ~۱۰ ثانیه بعد لینک ربات آماده می‌آید.

## 🌐 ماژول پروکسی (نسخه ۲ — مدیریت تفکیک‌شده هر اینستنس)

> خواسته کارفرما: «خودم از طریق ربات‌ساز برای هر اینستنسی که باشه پروکسی لاگین و سندر
> اضافه کنم، حذف کنم، ادیت بزنم، تست بگیرم — کاربر اصلاً دخلی نداشته باشه.»

### معماری دومرحله‌ای

```
   ➕ افزودن/ویرایش/حذف/تست (پنل ادمین)
                  │
                  ▼
   🏭 استخر مرکزی factory_proxies  ←—— تست مداوم هر PROXY_CHECK_INTERVAL
                  │ (انبار واحد + ماشین وضعیت active/weak/dead/disabled)
                  ▼
   🎯 جدول تخصیص instance_proxies (order_id + proxy_id + usage_type)
                  │  login = فقط لاگین | sender = فقط ارسال | both = هردو
                  ▼
   🔄 سینک اختصاصی: هر اینستنس فقط پروکسی‌های خودش را در جدول proxies
      دیتابیس خودش می‌گیرد (با usage_type خودش) — سندر و لاگین جدا
```

### دو سطح مدیریت

**۱) استخر مرکزی** (`/proxies`): انبار واحد پروکسی + تست مداوم + ویرایش/حذف با اثر
روی همه اینستنس‌ها + نمای جزئیات هر پروکسی (چه اینستنس‌هایی دارد).

**۲) پنل هر اینستنس** (`/panel → 🛡️ مدیریت پروکسی‌ها → 🗂 پروکسی اینستنس‌ها`
یا دکمه 🌐 پروکسی کنار هر ربات در لیست اینستنس‌ها):

| امکان | توضیح |
|---|---|
| ➕ افزودن پروکسی جدید | لیست چندخطی (تا ۳۰۰ خط) مستقیم برای این اینستنس — نوع (لاگین/سندر/هردو) انتخاب می‌شود؛ در استخر مرکزی هم ذخیره و بلافاصله تست می‌شود |
| 🎯 تخصیص از استخر مرکزی | انتخاب هوشمند بهترین‌ها: اول کم‌بارترین (توزیع بار بین اینستنس‌ها) بعد کم‌پینگ‌ترین — عدد یا all |
| 📋 لیست + جزئیات | هر تخصیص با وضعیت سلامت/پینگ/نوع + وضعیت واقعی در دیتابیس آن ربات (in_use، fail_count) |
| ⚡ تست | تست زنده تک پروکسی یا همه پروکسی‌های همین اینستنس (اتصال از طریق خود پروکسی به DC تلگرام) |
| ✏️ ویرایش | تغییر آدرس/اعتبارنامه — فقط همین اینستنس به پروکسی جدید منتقل می‌شود، بقیه دست نمی‌خورند |
| 🔀 تغییر نوع | لاگین ↔ سندر ↔ هردو (تخصیص تکراری هم پروکسی هم اینستنس → خودکار ارتقا به هردو) |
| ⏸/▶️ غیرفعال/فعال | خارج/برگرداندن موقت پروکسی از این اینستنس بدون حذف |
| 🗑 حذف | تک تخصیص / همه تخصیص‌های مرده / همه تخصیص‌ها (با تأیید دومرحله‌ای) |
| 📄 خروجی متنی | بکاپ پروکسی‌های همین اینستنس با نوع و وضعیت |
| 🔄 سینک فوری | اعمال فوری تخصیص‌ها در دیتابیس همین اینستنس |

### تخصیص خودکار موقع ساخت ربات جدید

با `AUTO_ASSIGN_ON_PROVISION=true` (پیش‌فرض)، به محض deploy موفق هر اینستنس،
`AUTO_ASSIGN_LOGIN_COUNT` پروکسی لاگین + `AUTO_ASSIGN_SENDER_COUNT` پروکسی سندر
بهترینِ استخر (با توزیع بار) خودکار تخصیص می‌یابد — مشتری هیچ دخالتی ندارد و
ربات از لحظه تحویل آماده لاگین و ارسال است. اگر استخر کم داشته باشد ادمین هشدار می‌گیرد.

### سازگاری با نسخه قبل (حالت legacy)

اینستنس‌هایی که هنوز هیچ تخصیص اختصاصی ندارند، دقیقاً مثل قبل از چرخش عمومی
استخر سالم استفاده می‌کنند (`PROXIES_PER_INSTANCE`). اولین باری که ادمین برای
اینستنسی پروکسی اختصاصی ثبت کند، آن اینستنس به حالت اختصاصی می‌رود. حذف همه
تخصیص‌ها → بازگشت به legacy.

### رفع باگ‌های نسخه قبل (اعمال‌شده)

- 🔧 حذف پروکسی از استخر مرکزی حالا ردیفش را در دیتابیس «همه» اینستنس‌ها
  غیرفعال می‌کند (قبلاً فعال می‌ماند و لاگین روی آن می‌نشست).
- 🔧 سینک حالا `usage_type` هر ردیف را از تخصیص همان اینستنس می‌نویسد
  (قبلاً همیشه login بود — پروکسی سندر عملاً غیرفعال بود).
- 🔧 اعلان مرگ پروکسی حالا نام اینستنس‌های متأثر و نوع استفاده را می‌گوید.

### تست مداوم و هندلینگ (مثل قبل + آگاهی از اینستنس)

هر `PROXY_CHECK_INTERVAL` (پیش‌فرض ۱۸۰ ثانیه) همه پروکسی‌ها از طریق خودشان به
DC تلگرام وصل می‌شوند:

| وضعیت | شرط | عکس‌العمل خودکار |
|---|---|---|
| 🟢 active | پینگ < 1200ms | در لیست سینک اینستنس‌های دارای تخصیص |
| 🟡 weak | پینگ > 1200ms | سینک می‌شود ولی اولویت آخر در انتخاب |
| 🔴 dead | ۳ شکست پیاپی | فوراً از همه اینستنس‌های دارای تخصیص خارج می‌شود + اعلان با نام اینستنس‌ها |
| ♻️ بازیابی | ۲ موفقیت پیاپی | خودکار برمی‌گردد به سرویس |

> 💡 نیازی به تغییر کد sender_bot نیست — سینک از طریق همان جدول proxies انجام
> می‌شود که پروژه از قبل می‌شناسد: لاگین (`usage_type IN ('login','both')`) و
> سندر (`claim_proxy_for_account` با `usage_type IN ('sender','both')`).

> 🗄 مهاجرت: جدول `instance_proxies` در اولین اجرا خودکار ساخته می‌شود
> (`init_db` → `create_all`)؛ نیازی به دستور SQL دستی نیست.

## 🆕 نسخه ۳ — سفارش با ساخت دستی پشتیبانی + ویدیوی آموزشی

### تغییرات کلیدی این نسخه (طبق خواسته کارفرما)

| # | تغییر | جزئیات |
|---|---|---|
| ۱ | **سفارش سندر → ساخت دستی پشتیبانی** | کاربر پلن را داخل ربات انتخاب می‌کند، توکن را ارسال می‌کند و هزینه از کیف پول کسر می‌شود؛ سپس سفارش با وضعیت `awaiting_approval` به پشتیبانی ارجاع می‌شود تا **ایمیج ربات را بسازد** (به‌جای دیپلوی خودکار). با `MANUAL_BUILD_MODE=false` رفتار خودکار قدیمی برمی‌گردد. |
| ۲ | **چک شارژ بودن هنگام انتخاب پلن** | اگر موجودی کیف پول کاربر کمتر از قیمت پلن باشد، پیام «موجودی کافی نیست» + دکمه‌های شارژ/پشتیبانی نمایش داده می‌شود و کاربر وارد فلوی توکن نمی‌شود. |
| ۳ | **متن جدید دکمه پنل‌ها** | متن رسمی کارفرما (`PLAN_TOKEN_GUIDE` در `bot/handlers/user_order.py`) با خط پایانی «⭕️ لطفا الان همینجا توکن ربات خودتون رو بدون هیچ چیز اضافه ای بفرستید👇👇:» هنگام انتخاب پلنِ حسابِ شارژ‌شده ارسال می‌شود. متن دکمه «📖 راهنمای دریافت توکن» **دست‌نخورده** باقی مانده است. |
| ۴ | **ویدیوی آموزشی توکن (اختیاری و بی‌خطا)** | اگر ویدیو تنظیم شده باشد، همراه «متن دکمه پنل‌ها» و «راهنمای دریافت توکن» ارسال می‌شود؛ اگر نباشد، متن‌ها بدون ویدیو ارسال می‌شوند و **هیچ خطایی رخ نمی‌دهد**. آپلود از پنل ادمین بدون ری‌استارت. |
| ۵ | **شارژ حساب → فقط پیوی پشتیبانی** | صفحه شارژ، **قیمت همه پنل‌ها** را نمایش می‌دهد و کاربر را به پیوی پشتیبانی هدایت می‌کند (دکمه شیشه‌ای). فلوی قدیمیِ «ارسال رسید داخل ربات» حذف شد؛ پشتیبانی از پنل ادمین (💳 شارژ حساب کاربر) موجودی را شارژ می‌کند. |
| ۶ | **اکانت مجازی → دکمه ربات خرید شماره** | در صفحه «📱 نیاز به اکانت تلگرامی؟» به‌جای دکمه پشتیبانی، **دکمه شیشه‌ای «🛒 خرید شماره مجازی \| Plus Number»** نمایش داده می‌شود (لینک از `VIRTUAL_NUMBER_BOT` در `.env`). |
| ۷ | **متن راهنمای جدید** | متن «🎧 راهنما و پشتیبانی» کاملاً بازنویسی شد (راهنمای جامع سرویس: فان سندر چیه، مراحل سفارش، ربات‌های من، ...) و دیگر شبیه متن سفارش نیست. |

### 🔧 فلوی سفارش در حالت دستی (پیش‌فرض)

```
کاربر → /start → «🛍️ سفارش سندر» → انتخاب پلن
   ├─ موجودی کافی نیست → پیام + «💳 شارژ حساب» + «👨‍💻 پشتیبانی» (شارژ در پیوی پشتیبانی)
   └─ موجودی کافی  → متن رسمی پنل‌ها + ویدیو → ارسال توکن → API_ID/HASH → کانال (اختیاری)
                     → خلاصه → «💳 پرداخت از کیف پول و ثبت سفارش»
                     → کسر اتمیک موجودی + ثبت سفارش (awaiting_approval)
                     → اطلاع پشتیبانی با ۳ دکمه:
                        ├─ 🏗 تأیید و ساخت خودکار   (appr → دیپلوی فکتوری مثل قبل)
                        ├─ 🔧 ساخت دستی انجام شد     (mb:done → deployed + انقضا + خبر به مشتری)
                        └─ 💰 رد و عودت وجه          (mb:refund → rejected + عودت کامل به کیف پول)
```

### 🎬 ویدیوی آموزشی — دو راه تنظیم

1. **پنل ادمین (توصیه‌شده):** `/panel` → «🎬 ویدیوی آموزشی توکن» → «📤 آپلود» → ویدیو/گیف/فایل بفرستید.
   ذخیره در جدول `app_settings` — **از همان لحظه، بدون ری‌استارت**، همراه متن‌ها ارسال می‌شود.
2. **فایل `.env`:** `TOKEN_GUIDE_VIDEO_FILE_ID=<file_id>` (فقط fallback اولیه؛
   با پیشوند `animation:` یا `document:` برای نوع غیر ویدیو).

اگر هیچ‌کدام تنظیم نباشد: متن‌ها بدون ویدیو ارسال می‌شوند — **صفر خطا**. ✅

### 💳 شارژ حساب (فقط پیوی پشتیبانی)

- کاربر: «💳 شارژ حساب» → قیمت پنل‌ها را می‌بیند → دکمه «👨‍💻 ارتباط با پشتیبانی (شارژ حساب)».
- پشتیبانی: پرداخت را در پیوی دریافت می‌کند → `/panel` → «💳 شارژ حساب کاربر» →
  ID عددی کاربر (از صفحه پروفایل کاربر) → مبلغ → تأیید دو مرحله‌ای → موجودی شارژ و به کاربر خبر داده می‌شود.

### 🆕 جدول دیتابیس جدید

| جدول | کاربرد |
|---|---|
| `app_settings` | key/value — ذخیره فایل‌آیدی ویدیوی آموزشی توکن (ساخت خودکار در اولین اجرا) |

## 🛡 چهار تله‌ی بزرگ — همگی اعمال شده‌اند

| # | تله | راه‌حل اعمال‌شده در همین کد |
|---|---|---|
| ۱ | **FERNET_KEY تکراری** = سشن‌های همه مشتری‌ها با یک کلید | `Fernet.generate_key()` یکتا برای هر اینستنس + ذخیره در دیتابیس فکتوری + بکاپ شبانه `.env`ها |
| ۲ | **Too many connections** در MySQL مشترک | `my.cnf` با `max_connections=1000` + پول اتصال هر اینستنس `POOL_SIZE=5`/`MAX_OVERFLOW=10` (۱۵ کانکشن) → سقف ۶۳ اینستنس فعال |
| ۳ | **امنیت Docker** (تزریق دستور از ورودی کاربر) | همه فرمان‌ها با **لیست آرگومان** (بدون shell)، نام کانتینر از `order_id` عددی، توکن قبل از دیپلوی با `getMe` اعتبارسنجی، guard مسیرها |
| ۴ | **هضم منابع** توسط یک مشتری | `mem_limit: 512m` + `cpus: 0.5` + `pids_limit` + چرخش لاگ + صف دیپلوی چندکارگره |

## 📈 ظرفیت و مقیاس‌پذیری — آماده ۵۰ سفارش همزمان

سه سقف زیر به‌صورت پیش‌فرض برای ۵۰ سفارش همزمان تنظیم شده‌اند (همگی از `.env` قابل تغییر):

| منبع | فرمول | پیش‌فرض فعلی | سقف |
|---|---|---|---|
| اسلات Redis | `NUM_REDIS × 15` | ۴ کانتینر | **۶۰ اینستنس** |
| کانکشن MySQL | `(MYSQL_MAX_CONNECTIONS − 50) ÷ (POOL + OVERFLOW)` | (1000−50)÷15 | **۶۳ اینستنس** |
| صف دیپلوی | `DEPLOY_QUEUE_SIZE` | ۲۰۰ جاب، ۲ کارگر | **موج ۵۰ سفارش ≈ ۲۵ دقیقه** |

> ⚠️ اگر در /panel خط «ظرفیت» به سقف نزدیک شدید:
> 1. `NUM_REDIS` را زیاد + کانتینر `factory_redis_5` و volume آن را به `docker-compose.yml` اضافه کنید
> 2. `docker compose -f docker-compose.yml --env-file .env up -d` و سپس `systemctl restart bot-factory`
> 3. برای سقف MySQL: هم `my.cnf` و هم `MYSQL_MAX_CONNECTIONS` در `.env` را با هم بالا ببرید

> نکته: `MAX_PENDING_ORDERS=3` سقف سفارش «در انتظار تأیید» به ازای هر کاربر است (ضد اسپام) — مانع ۵۰ مشتری مختلف نمی‌شود.

## 🔁 به‌روزرسانی همه ربات‌ها (قدرت روش ایمیج)

```bash
cd /opt/factory/source/sender_bot
git pull        # یا rsync سورس جدید
bash /opt/bot_factory/scripts/build_sender_image.sh     # build جدید + تگ تاریخ

# راه‌اندازی مجدد همه اینستنس‌ها (بدون از دست رفتن داده — bind-mount هستند):
for d in /opt/factory/instances/bot_*; do
  id=$(basename "$d" | cut -d_ -f2)
  docker compose -p "bot_$id" -f "$d/compose.yml" up -d --force-recreate
done
# rollback:  docker tag sender_bot:20260101 sender_bot:v1  و تکرار همین حلقه
```

## 🩺 عیب‌یابی سریع

| نشانه | علت / راه‌حل |
|---|---|
| `Too many connections` | `docker exec factory_mysql mysql -uroot -p… -e "SHOW VARIABLES LIKE 'max_connections';"` باید 1000 باشد (هم‌اندازه `MYSQL_MAX_CONNECTIONS` در `.env`)؛ my.cnf مونت شده؟ |
| سفارش fail: «image not found» | `bash scripts/build_sender_image.sh` هنوز اجرا نشده |
| «ظرفیت Redis پر است» | `NUM_REDIS` در `.env` را زیاد کنید + کانتینر redis جدید در `docker-compose.yml` + `docker compose up -d` + ری‌استارت ربات |
| سینک پروکسی fail برای اینستنس تازه | طبیعی است تا جدول‌ها ساخته شوند (~۱ دقیقه)؛ سیکل بعدی خودش ردیف می‌شود |
| instance بعد از استارت خاموش | `docker logs --tail 100 bot_{id}` — معمولاً توکن/PORT یا رمز DB در `.env` |
| دیسک پر شد | `docker system df`؛ لاگ‌ها محدود شده‌اند ولی volumes دانلود مشتری‌ها را چک کنید |

## 📋 نگهداری روزانه (۵ دقیقه)

- `journalctl -u bot-factory -e` — سلامت ربات فروش
- `/proxies` — آمار پروکسی‌ها (حداقل ۲ برابر تعداد نیاز داشته باشید)
- `docker stats --no-stream` — مصرف RAM/CPU اینستنس‌ها
- بکاپ شبانه فعال است؟ `ls -lh /opt/factory/backups/`
- **هر هفته یک بکاپ را خارج از سرور کپی کنید** (FERNET_KEYS قابل بازسازی نیستند!)
